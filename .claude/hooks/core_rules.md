[CORE RULES: 매 턴 강제적용. 아래 항목은 협상 불가.]
0. CAUTION: 명시적 지시 전 코드 수정 금지. 명시적 지시 전 커밋/푸시 금지.
1. 함수 호출을 인자로 중첩하지 말고 의미 있는 중간변수로 추출한다. (짧으면 허용)
2. 의미 있는 변수명을 사용하고, 메서드명은 동작이 명확히 드러나게 작성한다. tmp/temp/data/단일 문자(루프 인덱스 i, j 제외) 금지.
3. 조건 분기는 오류 케이스를 먼저 처리하고 early-return (guard clause) 패턴을 적용한다.
4. 1회 사용하는 private helper는 되도록 인라인으로 작성하고, 부득이한 경우 메서드 안에 중첩 함수로 작성한다. 유사 패턴이 반복될 때만 추상화한다.
5. 코드로 충분히 설명되면 주석을 쓰지 않는다. 주석은 이유만 간결히 적는다.
6. 구현 전: 가정 명시. 불확실하면 질문. 복수 해석 시 옵션 제시(묵시적 선택 금지). 더 단순한 방법이 있으면 먼저 언급. 제약과 규칙이 충돌하면 임의로 절충하지 말고 보고 후 지시를 받는다.
7. Surgical: 요청 범위만 수정. 인접 코드/주석/포맷 임의 개선 금지. 기존 dead code는 언급만, 삭제 금지. 내 변경이 만든 orphan만 제거.
8. 새 것을 만들기 전 같은 종류의 기존 사례를 먼저 열어 관례를 확인하고 따른다. 다르게 하려면 구현 전에 보고. 구조 변경 후에는 관례 일치 여부를 확인한다.
9. 연관 파라미터 3개 이상은 객체로 묶고, 호출 체인 끝까지 객체 그대로 전달(중간 해체 금지).
10. 새 로직 작성 전 같은 기능의 기존 유틸을 탐색해 재사용한다 — 지금 수정 중인 파일 내부부터 확인. 작업 후 내가 추가한 코드에 기존 helper와 중복되는 패턴이 없는지 점검한다.
11. 존댓말. 결론 먼저. 슬랭/과도한 이모지 금지. 검증된 사실과 의견 구분.
12. 타입 명시 필수: 함수 파라미터·반환 타입 힌트, 변수 선언 시 `:타입` 어노테이션. 타입 추론이 자명한 리터럴 대입만 생략 허용.
13. Parse, don't validate: 외부 입력(dict/JSON)은 검증만 하고 raw로 넘기지 말고, 검증을 거쳐야만 생성되는 불변 객체로 파싱해 전달한다.
